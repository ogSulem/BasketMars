## Аннотация

Выпускная квалификационная работа посвящена проектированию и разработке мобильного игрового приложения «BasketMars» для платформы Android. В приложении реализованы физически корректная модель броска мяча в кольцо на основе квадратичной кривой Безье, четыре игровых режима (в том числе онлайн-матчмейкинг с реальным соперником через Firebase Firestore), прогрессивная система сложности с динамическими препятствиями, система комбо-бросков, восемь достижений с разблокируемым инвентарем скинов, двуязычный интерфейс (русский и английский) и аутентификация через Google Sign-In. Весь игровой движок, физика, анимации и эффекты реализованы средствами нативного Android SDK (Software Development Kit – комплект инструментов разработчика) (Java, Canvas API (Application Programming Interface – программный интерфейс)) без применения сторонних игровых фреймворков. Хранение данных осуществляется посредством локальной реляционной базы данных Room (SQLite) и облачного хранилища Firebase Firestore. Результатом работы является полнофункциональное приложение, готовое к публикации в Google Play.

Ключевые слова: Android, Java, Canvas API, Firebase Firestore, Room, Google Sign-In, аркадная игра, матчмейкинг, ИИ-бот, квадратичная кривая Безье, паттерны проектирования.

Объем работы: 72 страницы, 13 рисунков, 14 таблиц, 18 источников, 5 приложений.

## Введение

Мобильный рынок игровых приложений является одним из наиболее быстро растущих сегментов IT-индустрии. По данным аналитической компании Sensor Tower, совокупная выручка от мобильных игр в 2023 году превысила 100 млрд долларов США [18]. Жанр аркадных игр занимает лидирующую позицию по количеству установок: механика «еще одного броска» обеспечивает высокий удерживающий потенциал при минимальном пороге вхождения [17].

Актуальность данной работы определяется двумя факторами. Во-первых, среди существующих мобильных баскетбольных игр практически отсутствуют нативные Android-решения с честной физической детекцией попадания, онлайн-матчмейкингом без выделенного backend-сервера и полноценной офлайн-работой. Во-вторых, разработка игрового движка средствами Android Canvas API представляет собой нетривиальную учебно-исследовательскую задачу, охватывающую широкий спектр современных архитектурных практик.

Степень разработанности проблемы. Вопросы разработки мобильных игровых приложений для платформы Android в академической и профессиональной литературе освещены неравномерно. Применение Canvas API для реализации игровой физики подробно рассмотрено в документации Android Developers [3] и профессиональной литературе [12]. Методы проектирования архитектуры мобильных приложений по принципам Clean Architecture исследованы R. C. Martin [13]. Подходы к реализации мультиплеерных мобильных игр без выделенного сервера описаны V. Romanuke [15]. Алгоритмические основы построения ИИ (искусственный интеллект)-агентов с адаптивным поведением изложены S. Russell и P. Norvig [16]. Особенности интеграции Firebase Firestore в Android-приложения рассмотрены в официальной документации [9] и руководстве R. Grantham [11]. Вместе с тем комплексная реализация нативного игрового движка с одновременной поддержкой физически корректной модели броска, бесцентрового онлайн-матчмейкинга, ИИ-бота с адаптивным поведением и системы прогрессии достижений на платформе Android без сторонних игровых фреймворков в указанных источниках не рассматривалась.

Краткий обзор аналогов показывает следующее. Среди существующих мобильных баскетбольных игр NBA 2K Mobile использует трехмерный движок и частичную офлайн-поддержку; Basketball Stars реализует онлайн PvP (Player vs. Player – игрок против игрока), но лишен офлайн-режима; Dunk Hit и Ball Blast не поддерживают сетевую игру. Ни одно из перечисленных приложений не сочетает одновременно онлайн PvP, полноценный офлайн-режим, физически корректную модель броска и открытый исходный код. Подробный сравнительный анализ приведен в разделе 1.2.

Цель работы – разработать полнофункциональное мобильное приложение игрового жанра «BasketMars» с применением нативного Android SDK, современных архитектурных паттернов, облачных сервисов Firebase и реляционной базы данных Room.

Для достижения цели поставлены следующие задачи:

1. Провести обзор рынка мобильных игровых приложений и сравнительный анализ существующих аналогов, выявить технические и функциональные пробелы, обосновать выбор технологического стека.

2. Спроектировать многослойную архитектуру приложения, разработать физически корректную модель броска на основе квадратичной кривой Безье, модель данных и схему пользовательского интерфейса.

3. Реализовать игровой движок средствами Android Canvas API, онлайн-матчмейкинг через Firebase Firestore без выделенного сервера, ИИ-бота с адаптивным поведением и систему прогрессии пользователя (достижения, инвентарь скинов).

4. Провести комплексное тестирование приложения: unit-тестирование, функциональное тестирование на реальных устройствах и анализ производительности.

Объект исследования – процесс разработки нативного мобильного игрового приложения для платформы Android.

Предмет исследования – методы и инструменты реализации игровой физики, многопользовательского режима и архитектурных паттернов в Android-приложении без применения сторонних игровых движков.

Методы исследования: анализ литературы и документации, проектирование на основе принципов SOLID (Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion), объектно-ориентированное программирование, тестирование (unit-тесты на JUnit 4), экспериментальная проверка на реальных устройствах.

Практическая значимость: разработанное приложение готово к публикации в Google Play; исходный код открыт на GitHub и может служить учебным примером нативной Android-разработки с Cloud-интеграцией.

Структура работы: работа состоит из введения, четырех глав, заключения, списка использованных источников и пяти приложений. Первая глава посвящена анализу предметной области и выбору технологий. Вторая глава описывает проектирование приложения. Третья глава рассматривает реализацию. Четвертая глава содержит результаты тестирования.

Список использованных источников оформлен в соответствии с ГОСТ Р 7.0.100–2018 [1]. Работа выполнена на кафедре анализа данных и технологий программирования Института вычислительной математики и информационных технологий Казанского (Приволжского) федерального университета.

Аркадные игры занимают первое место по числу загрузок (32% от общего числа) [18]. Ключевой тренд последних лет – интеграция соревновательных онлайн-режимов: по данным App Annie, приложения с PvP-режимом демонстрируют на 40% более высокое удержание пользователей на 30-й день по сравнению с одиночными играми [6].

Основные технические вызовы при разработке аркадных игр для Android:

– минимальная задержка рендеринга (целевой показатель – 60 кадров/с);

– честная и предсказуемая физическая модель, обеспечивающая согласованность между визуальным представлением и игровой логикой;

– эффективная работа с сетью без выделенного backend-сервера;

– поддержка широкого диапазона устройств (API 21+, размеры экрана от 5 до 7 дюймов).

### 2.2. Архитектура приложения

Приложение спроектировано по трехуровневой архитектуре с четким разделением ответственности [13]. Архитектурно-технологическая диаграмма приложения представлена на рисунке Г.1 (см. Приложение Г).

Ключевые архитектурные решения:

– Паттерн Repository: класс `LeaderboardRepository` абстрагирует источники данных (Room и Firestore) от слоя UI. Приложение взаимодействует только с репозиторием, не зная о конкретной реализации хранилища.

– Паттерн Strategy через интерфейс `MatchClient`: алгоритм поведения соперника подменяется без изменения кода `GameView`. `DemoDuelClient` реализует ИИ-бота, `OnlinePvpClient` – реального соперника через Firestore. Оба реализуют единый интерфейс `MatchClient`.

– Паттерн Singleton: `AuthManager` и `MusicPlayer` существуют в единственном экземпляре на протяжении жизни приложения.

– Application-уровень инициализации: класс `BasketballGameApp` (наследник `Application`) инициализирует Firebase, Room и репозиторий один раз при старте процесса.

UML (Unified Modeling Language – унифицированный язык моделирования)-диаграмма ключевых классов представлена на рисунке Д.1 (см. Приложение Д).

### 3.1. Игровой движок и физика

Игровой движок реализован в классе `GameView`, наследующем стандартный `android.view.View` [3]. Такой подход позволяет встраивать игровое поле в любой `ViewGroup` без дополнительных фреймворков. Игровой цикл основан на механизме `invalidate() → onDraw()`, вызываемом каждые 16 мс (целевые 60 кадров/с).

Модель броска на основе квадратичной кривой Безье. Траектория мяча описывается кривой Безье второго порядка [14]:

```
B(t) = (1-t)² · P0 + 2t(1-t) · P1 + t² · P2,   t ∈ [0, 1]
```

где P0 – начальная позиция мяча, P2 – конечная точка (рассчитывается исходя из направления и силы свайпа), P1 – управляющая точка (формирует характерный «дугообразный» изгиб). Параметр t дискретизируется с шагом 0.02, что дает 50 точек траектории – достаточно для плавной анимации.

Преимущество перед классической параболой: управляющая точка P1 позволяет тонко настраивать «форму» броска в зависимости от игрового режима и уровня сложности, сохраняя визуальную предсказуемость для игрока [12].

Детекция попадания («честная физика»). Попадание определяется не по конечной точке кривой, а по геометрии обода кольца: мяч считается попавшим, если его траектория проходит сквозь внутреннее отверстие обода при условии отсутствия столкновения с металлическими краями. Данный подход устраняет «несправедливые» попадания, когда мяч визуально проходит мимо кольца, но засчитывается системой.

Система комбо-бросков. Каждое последовательное попадание инкрементирует счетчик `comboStreak`. При значении 3 и выше на экране отображается анимированный индикатор комбо с эффектом свечения. Значение `bestComboStreak` фиксирует рекорд сессии.

Визуальные эффекты. В игровом движке реализованы следующие эффекты: тряска экрана при касании обода (`shakeUntilMs`, `shakeAmpPx`); тряска кольца при касании (`rimShakeUntilMs`); вспышка при попадании (`impactFlashUntilMs`); волновая анимация сетки кольца (7 узлов, `netDx/netVx/netDy/netVy`); эффект конфетти (`ConfettiView`, 90 частиц, 10 цветов, 4 секунды). Вибрация реализована с учетом версии API [5]:

```java
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S) {
    VibratorManager vm = (VibratorManager)
        ctx.getSystemService(Context.VIBRATOR_MANAGER_SERVICE);
    if (vm != null) vm.getDefaultVibrator()
        .vibrate(VibrationEffect.createOneShot(40,
            VibrationEffect.DEFAULT_AMPLITUDE));
} else if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O) {
    Vibrator v = (Vibrator) ctx.getSystemService(Context.VIBRATOR_SERVICE);
    if (v != null) v.vibrate(
        VibrationEffect.createOneShot(40,
            VibrationEffect.DEFAULT_AMPLITUDE));
}
```

### 3.2. Реализация игровых режимов

В приложении реализованы четыре игровых режима, описанных перечислением `GameMode`:

– ARCADE – бесконечный режим с прогрессивным усложнением. По мере роста счета появляются горизонтально движущиеся препятствия (`showObstacle`, `showObstacle2`) и начинает двигаться кольцо (`movingHoop`, `hoopVX`);

– TIMED – ограничение по времени 60 секунд (`modeDurationMs = 60_000`). Отображается обратный таймер; по истечении времени вызывается `sessionListener.onSessionComplete()`;

– ONLINE_DUEL – дуэль против ИИ-бота `DemoDuelClient` с синхронизацией через интерфейс `MatchClient`;

– ONLINE_PVP – дуэль против реального игрока через Firebase Firestore, с матчмейкингом в `MatchmakingActivity`. В методе `initModeState()` режим устанавливает флаги `onlineMode = true` и `timedMode = true`, что активирует все визуальные функции онлайн-режима: отображение призрака мяча соперника, счет соперника в HUD (heads-up display – игровой интерфейс с ключевыми показателями), отправку снапшотов через `maybeSendSnapshot()`, анимацию смены кольца после гола соперника. Сравнение всех игровых режимов приведено в таблице 7.

### 3.3. ИИ-бот (DemoDuelClient)

`DemoDuelClient` реализует интерфейс `MatchClient` и имитирует поведение реального игрока-соперника [16]. Ключевые особенности реализации:

Адаптация темпа. Бот отслеживает скорость набора очков реальным игроком через метрику `playerScorePerSec`, вычисляемую с помощью экспоненциально взвешенного скользящего среднего (EWMA, Exponential Weighted Moving Average):

```java
playerScorePerSec = 0.75f * playerScorePerSec + 0.25f * instRate;
```

Коэффициент сглаживания 0.75 обеспечивает устойчивость к резким скачкам темпа.

Система «холодных серий». После 2+ попаданий подряд с вероятностью 55% активируется «холодная серия» из 4–8 обязательных промахов (`coldStreak`), что имитирует психологические «спады» реального игрока.

Банковские броски. С вероятностью 28% бот выбирает траекторию «от стенки» (банковский бросок): сначала движется к левой или правой границе экрана, затем к кольцу. Это создает разнообразие визуального поведения призрака.

Параметры вероятностей:

– базовый шанс промаха: 47%;

– максимальный шанс промаха: 88%;

– минимальный шанс промаха: 35%;

– дополнительный штраф за банковский бросок: +12%;

– интервал между бросками: 1800–5500 мс.

Позиция призрака бота обновляется каждые 16 мс через `Handler.postDelayed()` и передается в `GameView` через `applyGhostSnapshot()`.

### 3.4. Онлайн-мультиплеер через Firebase

Матчмейкинг. Алгоритм поиска соперника в `MatchmakingActivity` построен по принципу бесцентрового P2P-матчмейкинга (peer-to-peer – равноправное соединение без выделенного сервера) [15] и работает следующим образом (рисунок 4):

```
Игрок А                  Firestore                    Игрок Б
   │                         │                            │
   │─ set(pool/A, searching)─▶│                            │
   │                         │◀─ set(pool/B, searching) ──│
   │                         │                            │
   │◀─ snapshot(pool/*)  ────│                            │
   │                         │                            │
   │─ transaction: ──────────▶│                            │
   │   create match/{roomId}  │                            │
   │   update pool/A matched  │                            │
   │   update pool/B matched  │                            │
   │                         │                            │
   │                         │─── snapshot(pool/B) ──────▶│
   │                         │    status=matched          │
   │  enterGame(role=1) ─────│                            │
   │                         │               enterGame(role=2)
```

Рисунок 4. Схема алгоритма матчмейкинга

Транзакция Firestore гарантирует атомарность [7]: два игрока не могут одновременно создать два разных матча. Если за 30 секунд соперник не найден, происходит автоматический откат к режиму ONLINE_DUEL (бот).

Синхронизация счета. `OnlinePvpClient` подписывается на документ матча через `addSnapshotListener` [9]. При каждом обновлении счета соперника в Firestore колбэк `onGhostSnapshot()` вызывается на главном потоке. Для предотвращения избыточных записей в Firestore введено ограничение частоты (`SCORE_WRITE_INTERVAL_MS = 800 мс`) [11].

### 3.6. Локализация и настройки

Двуязычная поддержка реализована через стандартный механизм Android Resource Qualifiers: ресурсы на русском языке находятся в `res/values/strings.xml`, на английском – в `res/values-en/strings.xml`. Переключение языка производится в `SettingsActivity` с сохранением выбора в `SharedPreferences`.

Класс `LocaleHelper` применяет сохраненную локаль через метод `attachBaseContext`:

```java
public static Context wrap(Context ctx) {
    String lang = getSavedLang(ctx);
    Locale locale = new Locale(lang);
    Locale.setDefault(locale);
    Configuration config = new Configuration(
        ctx.getResources().getConfiguration());
    config.setLocale(locale);
    return ctx.createConfigurationContext(config);
}
```

Метод `attachBaseContext()` переопределен во всех семи Activity приложения в соответствии с жизненным циклом Activity Android [2].

Музыкальный плеер (`MusicPlayer`) работает с медиафайлами из `res/raw` (обнаружение происходит через Reflection API класса `R$raw`). Поддерживается перелистывание треков, пауза и возобновление воспроизведения при сворачивании/разворачивании приложения через `ActivityLifecycleCallbacks`.

Настройки аккаунта Google Sign-In реализованы в `SettingsActivity`. При успешной аутентификации Firebase UID сохраняется в `AuthManager` (singleton) и используется для атрибуции записей в облачном лидерборде [8]. Не авторизованные пользователи получают анонимный UUID (`anonymousId`), сохраненный в `SharedPreferences`.

```java
// EWMA-сглаживание скорости набора очков игроком
private void updatePlayerRate(int score, long now) {
    long dtMs = now - lastPlayerRateAtMs;
    if (dtMs >= 700) {
        int dScore = score - lastPlayerScoreForRate;
        float dt = Math.max(0.001f, dtMs / 1000f);
        float instRate = dScore / dt;
        playerScorePerSec = 0.75f * playerScorePerSec
                          + 0.25f * instRate;
        lastPlayerScoreForRate = score;
        lastPlayerRateAtMs = now;
    }
}

// Расчет вероятности промаха и активация холодной серии
private void executeShot(long now) {
    float missChance = 0.47f + 0.10f * scoreStreak
                             - 0.05f * missStreak;
    if (currentShotType != SHOT_DIRECT) missChance += 0.12f;
    if (coldStreak > 0) { coldStreak--; missChance = 1.0f; }
    missChance = clamp(missChance, 0.35f, 0.88f);

    boolean miss = random.nextFloat() < missChance;
    if (!miss) {
        remoteScore++;
        scoreStreak++;
        if (scoreStreak >= 2 && random.nextFloat() < 0.55f) {
            coldStreak = 4 + random.nextInt(5);
            scoreStreak = 0;
        }
    } else {
        missStreak++;
        scoreStreak = 0;
    }
}
```

## Приложение Б

### Реализация метода handleFairScoring и геометрии обода

Метод `handleFairScoring` реализует двухфазную геометрическую детекцию попадания мяча в кольцо. Вместо проверки по конечной точке траектории метод анализирует каждый шаг анимации, что устраняет «несправедливые» попадания при быстрых бросках:

```java
private void handleFairScoring(float prevX, float prevY) {
    if (gameOver) return;
    if (scored) return;
    // Засчитываем только нисходящее движение (мяч летит вниз)
    if (velocityY <= 0) return;

    // Сужаем допуск на ширину мяча, чтобы визуальный проход
    // точно соответствовал геометрии обода
    float left  = rimInnerLeft  + ballRadius * 0.25f;
    float right = rimInnerRight - ballRadius * 0.25f;
    if (left >= right) return;

    // Фаза 1: мяч вошел в отверстие сверху
    float prevBottom = prevY + ballRadius;
    float currBottom = ballY + ballRadius;
    boolean crossesTopDown = prevBottom < rimYTop && currBottom >= rimYTop;
    if (crossesTopDown && ballX > left && ballX < right) {
        enteredHoop = true;
    }

    // Фаза 2: мяч полностью прошел сквозь отверстие снизу
    if (enteredHoop) {
        float prevTop = prevY - ballRadius;
        float currTop  = ballY - ballRadius;
        boolean passesThrough = prevTop < rimYBottom && currTop >= rimYBottom;
        if (passesThrough && ballX > left && ballX < right) {
            onScored();
        }
    }
}
```

Параметры геометрии обода. Кольцо определяется шестью координатными переменными, обновляемыми методом `spawnHoop()` при каждом создании нового кольца:

```
rimX, rimY          — верхний левый угол описывающего прямоугольника
rimW, rimH          — ширина и высота кольца (3D-эллипс)
rimInnerLeft        — X левого края внутреннего отверстия
rimInnerRight       — X правого края внутреннего отверстия
rimYTop             — Y верхней плоскости отверстия обода
rimYBottom          — Y нижней плоскости отверстия обода
```

Схема геометрии обода (вид сбоку):

```
         rimX                   rimX+rimW
          │←──────── rimW ────────▶│
          │                        │
rimYTop ──┼────────────────────────┼── верхняя плоскость
          │  rimInnerLeft          │
          │      │←── hole ──▶│   │
rimYBottom┼──────┼─────────────┼───┼── нижняя плоскость
          │      │             │   │
          └──────┴─────────────┴───┘
```

Рисунок Б.1 – Геометрическая схема обода кольца

Двухфазный алгоритм гарантирует, что мяч получит очко только при прохождении сквозь внутреннее отверстие сверху вниз. Броски «сзади» (снизу вверх) и касания края обода не засчитываются. Это соответствует реальным правилам баскетбола и обеспечивает предсказуемость игровой механики.

DAO для таблицы `leaderboard_entries`:

```java
@Dao
public interface LeaderboardDao {
    @Insert(onConflict = OnConflictStrategy.REPLACE)
    long insert(LeaderboardEntry entry);

    @Query("SELECT playerName, mode, MAX(score) AS score, "
         + "MIN(timestamp) AS timestamp, 0 AS id "
         + "FROM leaderboard_entries WHERE mode = :mode "
         + "GROUP BY playerName, mode "
         + "ORDER BY score DESC, timestamp ASC LIMIT :limit")
    List<LeaderboardEntry> getTop(String mode, int limit);

    @Query("SELECT MAX(score) FROM leaderboard_entries "
         + "WHERE mode = :mode AND playerName = :playerName")
    Integer getBestScore(String mode, String playerName);

    @Query("SELECT COUNT(*) FROM leaderboard_entries")
    int countAll();
}
```
